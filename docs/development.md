# Helix development environment

Helix runs in a ROS 2 Lyrical container alongside the compiler and language
servers. The host checkout is mounted at `/workspace`; edits are immediately
visible on the host. ROS headers, Python modules and package resources are under
`/opt/ros/lyrical` in the editor's own filesystem.

## Start editing

From the repository root:

```bash
podman-compose --profile dev build dev
podman-compose --profile dev run --rm dev
```

The second command opens Helix. To open a particular file or a shell:

```bash
podman-compose --profile dev run --rm dev hx compose.yaml
podman-compose --profile dev run --rm dev bash
```

Docker users can replace `podman-compose` with `docker compose`. The development
profile keeps the editor out of the ordinary simulation startup. The `dev`
container itself needs no GPU or X11 access, though the shared Compose file still
requires the desktop's `XAUTHORITY` variable when parsing the sim service.

Rootless Podman maps the container's root user to your host user, so new workspace
files belong to you. With rootful Docker, pass `--user "$(id -u):$(id -g)"` to
`run` to keep host ownership, and set a writable `HOME` with `-e HOME=/tmp`.

## Language support

| Language | Server | Dependency lookup |
| --- | --- | --- |
| C / C++ | clangd | `ros2_ws/build/compile_commands.json` generated by colcon |
| Python | pylsp / Jedi | System Python with the ROS underlay and built workspace overlay sourced |
| YAML / Compose | yaml-language-server | YAML validation, completion and formatting |

Project settings live in `.helix/`. Formatting is explicit with `:format`; saving
a file does not reformat it automatically. C++ uses clangd's formatter and Python
uses autopep8. Installed package versions can be inspected with `hx --version`,
`clangd --version`, `pylsp --version` and `npm list --global --depth=0`.
`hx --health cpp` may report a missing optional debugger (`lldb-dap`); debugging
is not configured. A formatter shown as `None` means no separate formatter
command is configured; `:format` uses the language server.

Useful Helix commands:

- `Space f`: select a project file.
- `g d`: go to definition, including installed ROS headers and Python modules.
- `g r`: find references; `K`: show documentation for the symbol.
- `Ctrl-o`: return to the previous location.
- `:open /opt/ros/lyrical/share/rclcpp/package.xml`: inspect an installed resource.
- `:log-open`: inspect language-server errors.
- `:quit`: leave the editor and remove the temporary container.

Binary ROS packages provide installed headers, Python source and resources, not
necessarily the C++ implementation source. Definition lookup can therefore lead
to a declaration in a header; debugging a library's implementation may require
its source checkout. `/opt/ros` edits in a temporary container are discarded.

## Build ROS packages

Add packages beneath `ros2_ws/src`. Inside the development shell:

```bash
rosdep update
rosdep install --from-paths ros2_ws/src --ignore-src -r -y
scripts/ros-build
source ros2_ws/install/setup.bash
hx ros2_ws/src
```

Run the build helper from anywhere inside the container. It enables CMake's
compilation database; colcon aggregates C++ package commands in
`ros2_ws/build/compile_commands.json`. Build a C++ package before expecting clangd
to resolve all its includes and generated message headers. Refresh the build
after changing dependencies or compiler flags. Package dependencies must be
declared in `package.xml` and the build configuration.

The entrypoint sources the ROS underlay and any existing workspace overlay before
starting Helix or a shell. After the first build, or after adding Python packages,
source the overlay and restart Helix so its language servers inherit the updated
paths. `:lsp-restart` alone cannot change Helix's inherited environment.

Dependency installs made in a temporary container disappear on exit. Put regular
development dependencies in `docker/dev.Dockerfile` and rebuild the image.
Workspace `build`, `install`, `log` and cache directories persist on the host and
are ignored by Git. Do not share those build directories with a different host
toolchain or ROS distribution.

## Verify the environment

```bash
podman-compose --profile dev run --rm dev scripts/check-dev-env
```

This builds a disposable C++ ROS package, checks clangd against its compilation
database, resolves a Python ROS definition through Jedi, checks Helix language
support, and validates the development scripts and Compose YAML. It does not
start a robot or implement the ROS bridge.

For packages added to the workspace, run their lint and test targets before
committing, normally through `colcon test` followed by
`colcon test-result --verbose`. An empty workspace has no package tests yet.

## Access the existing duck

Start the simulation separately with `podman-compose up -d sim`. The development
container shares the existing socket and Rust build volumes:

```bash
podman-compose --profile dev run --rm dev robotctl health
```

This is the existing daemon CLI. ROS topics and Nav2 are still tracked as future
work in the [integration roadmap](ros2-roadmap.md).
